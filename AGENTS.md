
## Learned User Preferences

- Never start the dev server; the user always does this manually
- Add a file path comment at the top of every source file (e.g. `// src/components/sidebar/Sidebar.tsx`)
- Use Biome for linting/formatting — not ESLint or Prettier. The working tree is CRLF, so format touched files with `npx biome format --write --line-ending=crlf <files>`
- Prefer CSS variables + SCSS over Tailwind; no Tailwind dependency in this project
- Use Cascadia Code (not JetBrains Mono) as the monospace font
- No emojis in responses unless explicitly requested
- Prefer KISS, YAGNI, SOLID; propose incremental improvements and understand existing code first
- Always check available MCP servers and use them when relevant
- Commit only when asked, in logical batches (one commit per feature or section)
- Keep this file in step with the code: when a change makes a fact here wrong (stack, window, storage, shortcuts, release flow), fix that line in the same change. It is edited by hand

## Releases and changelog

- The changelog is written for the people using the app, not for developers: one short line per change, in plain language about what they see or can now do. No file, function or library names. The same text is shown in the GitHub release and in the app's update dialog
- Sections, in this order, with empty ones left out: `### New`, `### Changed`, `### Fixes`, `### Other`. Keep a release to a handful of lines; merge small tweaks into one line
- Add lines under `## Unreleased` at the top of `CHANGELOG.md` in the same change that ships the feature or fix, not at release time. The section heading is just `## vX.Y.Z` (no title, no date) once released
- Never edit version numbers by hand. Versions follow semver: patch = fixes only, minor = anything new, major = a change that breaks existing vaults
- To release, and only when the user asks: `npm version patch|minor|major` (or an exact number), then `git push --follow-tags`, then publish the draft release on GitHub. `npm version` (via `scripts/release.mjs`) checks the changelog format, bumps `package.json` and `src-tauri`, turns `## Unreleased` into `## vX.Y.Z`, commits "Release vX.Y.Z" and tags it. Never tag or push unasked
- `.github/workflows/release.yml` builds the signed Windows installer on a `v*` tag and opens a draft release whose notes are that CHANGELOG section. Installed apps only see published releases

- Tasks are a to-do app of their own, apart from the notes: the Notes | Tasks tabs at the top of the sidebar (`graphene.sidebarTab`, the open view in `graphene.taskView`). Data (`src/lib/taskStore.ts`, pure, tested, shared with the MCP server): lists (`TaskList`: optional `color`, one of six names whose colours are the `--accent-*` tokens, and optional `groupId`), groups, tasks (`title`, `done` / `doneAt`, `important`, `myDay`, `due`, `note`, `steps`, `order`) and steps (one level). `myDay` holds the day it was added and counts only while it equals today, so My Day empties itself; My Day and Important are views (`smartList`), not stored lists. Storage is hidden JSON per vault: `<vault>/.tasks/index.json` (`{ version, groups, lists }`) and `<vault>/.tasks/<listId>.json` (`{ version, tasks }`); dot folders are outside the notes scan. Parsing is tolerant: bad entries and repeated ids are dropped, ids that are not safe file names are rejected (an id becomes `<id>.json`), unknown keys are kept so a newer file survives an older app. The default list (`DEFAULT_LIST_ID`, "tasks") always exists in memory and is saved with the first change, so opening a vault writes nothing. Reducers are pure, take ids and timestamps as arguments and return their input when nothing matched. `src/lib/taskFiles.ts` is the file layer over a tiny `TaskFs` (`taskFsTauri.ts` for the app, `mcp/taskFsNode.ts` for the server): every change reads the file, applies the reducer and writes it back through a temp file, one at a time per file, so what the other side wrote in between is merged; a file that is not JSON is copied to `<name>.bak` before it is replaced, and one that cannot be read is never written over. `useTasks(vaultPath)` (in `MainApp`) applies each reducer to memory at once and repeats it on disk, rescans on window focus unless a write of its own is pending or ran meanwhile (the first load is retried) and not more often than every 5 s (`rescanDue` in `src/lib/rescanGate.ts`, the gate of the notes' rescan too: restoring a minimised window sends several focus events; a first load that has not landed is not held back), and gives `today`. Each plugin call of `taskFsTauri.ts` is an IPC round trip, so it keeps them down: it reads first and asks `exists` only after a failure (a missing file is null, one that exists and cannot be read still throws), and it makes the folder only when a write finds it missing, so a change of a list is 3 calls (read, temp file, rename) and a file that is there is read with 1 Order is a rank (`order`, `placeNear` as for notes): a new task goes on top, unranked tasks are newest first, lists and groups without a rank go by name. A task opens in a side pane (`TaskDetail`, `openTaskId`): docked to the right of the list, and floating over it (`@container main (max-width: 739px)`) when the panel is narrow; `TasksPane` sorts and splits the list in a `useMemo` (and `TaskRow` is `memo`, given `setDone`, `updateTask` and a `draggable` flag instead of the whole `api`), finds the open task in any list, so the pane stays when the task is moved, and keys the pane by task id so its uncontrolled fields restart; the pane sits in a slot (`tasks-pane__details`) that slides like the sidebar, so `TasksPane` keeps the last open task while it slides out (and keys that pane "closing", so reopening starts fresh); Enter or Space on a row focuses the pane's title, a click leaves the focus, Escape is one rule, as in a rename: it first drops what is being typed in a field (back to its saved text, the pane stays), the next Escape closes the pane and returns the focus to the row, and Enter commits; a task's checkbox and star, and a step's, are named with its title (`Mark "x" as done`); deleting one shows an `UndoToast` (`restoreTask` puts it back with its rank); so does deleting a list or a group: the delete banners count every task (ticked ones too) and `deleteList` / `deleteGroup` give back a snapshot (`ListSnapshot`: the entry with its colour, group and rank, and all its tasks; `GroupSnapshot`: the group and the ids of its lists), which `restoreList` / `restoreGroup` write back through the pure `restoreList`, `restoreTasks` and `restoreGroup` reducers of `taskStore` (the tasks file first, merged into what the file holds, then the index; a list whose group is gone returns outside any group, a list moved to another group meanwhile stays there, and a restore waits for the delete of that list if it is still writing, or it would write the file back before the delete removed it); `TaskLists` hands the snapshot to `App` through `onDeleted`; moving a task to another list writes the new file before it leaves the old one. - Storage: file-based vaults, each a user-chosen folder (config at `AppData/graphene/config.json` through Tauri `BaseDirectory.AppData`, see Vaults below). Every item is a `.md` file with YAML frontmatter named `{slug(title)}-{id}.md`; folders are real directories and a folder id is its path relative to the vault; deleted items move to the hidden `<vault>/.trash` and tasks live in the hidden `<vault>/.tasks` (dot folders are ignored by the scan); files that are not `.md` notes with an id are ignored (the v0.1.0 snippet files are no longer converted). Every note write (`saveItem`, the rename, restore, the MCP server's `writeNote`, `.folder-order.json`) goes through `writeAtomic`: a dot `.<name>.tmp` beside the target, then a rename, so a crash never leaves a half-written note or something the scan shows as a note. `replaceItemFile` writes the new file first and removes the old one after (best effort, and never when the two paths differ only in case); a failed write leaves the old note untouched. Failure contract (header of `storage.ts`): `saveItem`, `replaceItemFile`, `moveItemFile`, `trashItemFile`, `restoreItemFile`, `emptyTrashFiles`, the folder functions (`createFolderDir`, `renameFolderDir`, `moveFolderDir`, `deleteFolderDir`, `restoreFolderDir`) and `writeFolderOrder` reject when the write did not happen, and the hooks report it; only the best-effort steps just warn (removing the old file after a rename, the trash copy after a restore, `sweepUnusedImages`). `tracked` runs every write one at a time, in call order, so never call a `tracked` function from inside another one (it would wait for itself). Loading: `loadVault` (one call to the Rust `scan_vault`, typed in `src/lib/vaultScan.ts`) returns every note WITHOUT its text (`unloaded`), the folders with their ranks, the count of `.trash` notes and a `FileStamp` per note (relative path, mtime, size). `useItems.adoptScan` takes it and the sidebar paints; `useBodies` then reads the texts in batches (`readBodies`, `batchSize`: 300 to 2000 notes per `read_notes` call, one call at a time), each batch applied with one state update, in a transition, by `applyBodies`, which only fills a note that is still `unloaded` (a note typed in, saved or changed since the scan is never replaced by a text read earlier); a read that fails is retried once and reported once per scan, and the note stays unloaded. A note that is not loaded is NEVER written: `writeItem` rejects it (every write of a note, `saveItem`, `replaceItemFile` and `restoreItemFile`, goes through it, so no path can turn a file into an empty note), and the callers read the text first with `loadBodies` (a priority read of just those notes, a call of its own): `useItems` in `updateItem`, `moveItem` and `deleteItem` (the copy that goes to the trash is what Restore writes back), and `App` before it opens or edits a note (`NotePending` stands in until the text is in, so the editor never mounts on an empty body), duplicates one, or renames or deletes a folder (the files under it move, so their texts are read first, from where they still are). The trash is not read at start: the sidebar shows the scan's `trashCount` plus what was trashed since, and `loadTrash` (the Rust `scan_trash`, one call and metadata only: no texts) lists it when the Trash view first opens (`useItems.loadTrashList`, merged with `mergeTrash`). A trashed note is `unloaded` like a scanned one; `useItems.loadTrashBody` reads its text with `readBodies` (from the stamps in `trashFiles`) when it is restored or deleted for good, since Restore writes the text back. The scan rules (dot entries and the root `attachments` are skipped, `.md` only, a note needs an id, the folder a note sits in wins over its frontmatter, symlinks are not followed, the last file wins for a repeated id) and the frontmatter subset of `fileFormat.ts` live in two places that must change together: the Rust scan (`src-tauri/src/vault_scan.rs`, which replaced the TypeScript walker of `storage.ts`) and `mcp/vault.ts`; `parseNoteFile` is still the TypeScript parser, for the trash and dropped files. The shared contract is `fixtures/vault` (every edge case: CRLF, a byte order mark, bad bytes, quotes, ranks, dot and attachments folders, `.trash`, `.folder-order.json`; `fixtures/.gitattributes` keeps its bytes and Biome skips it) and `fixtures/vault.expected.json`: `fileFormat.test.ts`, `mcp/vault.test.ts` and `src-tauri/tests/vault_scan.rs` (`cargo test`) all check it, so change a rule and the fixture together. A save into a folder skips its `mkdir` call when an earlier save made sure of it (`madeDirs` in `storage.ts`, absolute paths): renaming or deleting a folder drops it and what is under it, a write that fails drops its folder, and `loadVault` and `rescanVault` clear them all, since something outside the app may have removed a folder (the first save into it makes it again). A write never makes the vault's own folder (`src/lib/vaultRoot.ts`): `mkdir` with `recursive` would turn a renamed, deleted or unplugged vault into an empty new one, with the save landing in it. Everything that is about to make a folder in a vault asks `requireRoot(vaultPath)` first (`writeItem`, so `saveItem`, `replaceItemFile` and `restoreItemFile`, then `moveItemFile`, `createFolderDir`, `moveToTrash`, `restoreFolderDir`, `saveImage`, and `taskFsTauri`'s first write into `.tasks`), which rejects with a `VaultMissingError` ("the vault folder is not there"; `reportError` puts that reason in the toast, `Could not save "Plan": the vault folder is not there`) when the folder is not there. A scan that lists the vault (`loadVault` and `rescanVault`, through `scanRoot`) marks the folder as seen, so the usual save costs no extra call; a failed scan or a failed write forgets it, so the next write looks again; subfolders below a vault that is there are made as before. A new place that writes into a vault must call `requireRoot` before any `mkdir`. The MCP server has the same guard: `requireVault(vault)` in `mcp/vault.ts` (a `stat`; it rejects with `vaultMissingError`) runs before `writeNote(vault, path, item)` makes anything, and before the first write into `.tasks` in `mcp/taskFsNode.ts`, so a vault whose folder is gone is an error there too and only the folders below it are made. One note leaves the trash for good through `emptyTrashFiles(vault, [note])` (`useItems.deleteForever`: it reads the note's text first; a failed removal is reported and the row stays; then `sweepUnusedImages(vault, ownImagesIn(text))` looks at only the pictures that note names and that are named like `saveImage` names them (`ownImagesIn`, `src/lib/attachments.ts`), and one that any other note, live or trashed, still links stays; a note whose text cannot be read leaves its pictures to the next Empty trash, whose sweep covers every picture)

# GitNexus — Code Intelligence

This project is indexed by GitNexus as **graphene** (619 symbols, 1132 relationships, 51 execution flows).

> Index stale? Run `node .gitnexus/run.cjs analyze --index-only` from the project root — it auto-selects an available runner. No `.gitnexus/run.cjs` yet? Bootstrap with `npx`, `bunx`, or `pnpm dlx` — e.g. `bunx gitnexus@latest analyze` (npm 11 npx crash; #1939).

## Always Do

- **MUST run impact before editing.** Use `impact({target: "symbolName", direction: "upstream"})` or `node .gitnexus/run.cjs impact "symbolName" --direction upstream --repo .`; report callers, processes, and risk. Never substitute grep for graph analysis.
- **MUST analyze graph changes before committing.** Use `detect_changes({scope: "all"})` (MCP) or `node .gitnexus/run.cjs detect-changes --scope all --repo .` (CLI fallback). `partial: true` or `truncated: true` is not a clean check — a zero means unseen, not unaffected; re-run it. For regression review: `detect_changes({scope: "compare", base_ref: "main"})` or `node .gitnexus/run.cjs detect-changes --scope compare --base-ref "main" --repo .`.
- MUST warn on HIGH/CRITICAL `risk` pre-edit; never use `riskSharedAxes` to waive a HIGH/CRITICAL `risk` warning. Compare File/symbol: MCP File omits axes; Graph-RAG expands File.
- **MUST treat `risk: UNKNOWN` as unresolved, not as low.** An empty caller set is not evidence the symbol is unused — it can also mean the callers are not resolvable by the index (plain-object property access, dynamic dispatch, cross-language calls). `impact` pairs `UNKNOWN` with a `riskNote` saying so. Confirm with a text search before treating the symbol as safe to change or delete; do not proceed on the strength of a zero.
- **MUST use `query({search_query: "concept"})` for concepts/flows, `context({name: "symbolName"})` for a named symbol, or `impact` for blast radius, on read-only callers, dependencies, imports, or execution flow.** Graph first; text search only for empty/`UNKNOWN`/literals.
- For security review, `explain({target: "fileOrSymbol"})` lists taint findings (source→sink flows; needs `analyze --pdg`).

## Never Do

- NEVER edit a function, class, or method before MCP/CLI impact analysis.
- NEVER ignore HIGH or CRITICAL risk warnings from impact analysis, and never read `UNKNOWN` as an all-clear — it means the walk could not answer, which is the one verdict that requires confirming by other means.
- NEVER rename symbols with find-and-replace — use `rename` which understands the call graph.
- NEVER commit before MCP/CLI graph change analysis.
